16. common/service/client.ts — Modify
In the !response.ok block, after the 401 handler, before the shared body-read code:

if (response.status === 503) {
    try {
        const body = await response.json() as any;
        if (body?.maintenanceMode) {
            window.dispatchEvent(new CustomEvent('maintenance:activated', {
                detail: { message: body.message ?? 'Platform is under maintenance' }
            }));
        }
    } catch {}
    throw new Error('Service temporarily unavailable');
}
This consumes the body once and always throws — the downstream let body = await response.json() on line 64 is never reached for 503s.

Edge Cases & Trade-offs
Concern	Resolution
Mid-session non-admin hits 503	client.ts interceptor fires maintenance:activated event → context flips to maintenance → ProtectedRoute/GuestRoute re-render → shows MaintenancePage
Double response.json() consumption	503 branch awaits body and always throws, so the shared body-read code is never reached for 503 responses
Infrastructure 503 (no maintenance flag)	Guarded by body?.maintenanceMode === true — false positives silently pass through as generic errors
prev scoping in event listener	Uses functional updater: setPublicConfig(prev => ({ ...prev, ... }))
App loading during maintenance	SystemConfigContext defaults to safe values (maintenanceMode: false) while loading — brief flash of normal app, then fetch resolves to maintenance state
WebSocket-driven features during maintenance	Not covered by HTTP interceptor; next HTTP-based fetch/navigation catches it. Documented acceptable tradeoff.
Admin toggles maintenance while on admin panel	Filter allows admin's JWT through; admin continues working normally
Non-admin on login page during maintenance	Banner shown, form still renders; backend rejects non-admin login attempts with 403 MAINTENANCE_MODE
